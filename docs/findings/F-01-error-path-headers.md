# \# F-01. Заголовки безпеки зникають на відповіді 500

# 

# \*\*Статус:\*\* Fixed

# \*\*Актив:\*\* заголовки X-Content-Type-Options і Referrer-Policy у відповідях API

# \*\*Компонент:\*\* конвеєр обробки запитів, src/SecureLab.Api/Program.cs

# \*\*Пріоритет:\*\* P3

# 

# \## Передумови і межі огляду

# 

# Commit початку огляду b41e0ea (v0.5.0); production-like профіль (`--no-launch-profile -c Release`, Hosting environment: Production); локальна навчальна база, якій навмисно змінено порт (54399), щоб вона була недосяжною; запит POST /api/auth/login з вигаданим паролем. Не перевірялись реальне розгортання і зворотний проксі.

# 

# \## Відтворення

# 

# 1\. Запустити API у production-like профілі з недосяжною базою.

# 2\. Надіслати POST /api/auth/login з вигаданими даними.

# 3\. Очікувалось: 500 Problem Details із заголовками X-Content-Type-Options: nosniff і Referrer-Policy: no-referrer, як на інших відповідях.

# 4\. Фактично: 500 Problem Details (title, status, traceId) без цих двох заголовків.

# 

# \## Вплив і ймовірність

# 

# \*\*Статус перевірки:\*\* спостережено локально.

# 

# Відповідь про помилку втрачає два захисні заголовки: браузер може вгадувати тип вмісту (MIME sniffing), а адреса сторінки може потрапити в заголовок Referer. Це послаблення захисту, а не прямий витік даних. Сценарій доступний будь-якому клієнту, коли виникає необроблена помилка. Оцінку за CVSS не виконувалось.

# 

# \## Першопричина

# 

# Заголовки виставлялись у проміжному обробнику перед `next()`. Коли виникає виняток, `UseExceptionHandler` очищає відповідь перед формуванням Problem Details, тому раніше виставлені заголовки зникають.

# 

# \## Виправлення

# 

# Заголовки виставляються в обробнику `Response.OnStarting`, який спрацьовує в момент початку надсилання відповіді, тобто після того, як `UseExceptionHandler` сформував 500. Для Referrer-Policy використано індексатор замість Append, щоб значення не дублювалось. Порядок конвеєра не змінено, другого обробника помилок не додано. Коміт 4ce3215.

# 

# \## Retest

# 

# Той самий запит після виправлення: 500 Problem Details містить X-Content-Type-Options: nosniff і Referrer-Policy: no-referrer.

# 

# \## Positive regression

# 

# Звичайна відповідь 200 має обидва заголовки по одному разу (значення не задвоїлись); на відповідях 400 і 404 заголовки лишились. Повний набір тестів проходить (24 з 24 після змін ЛР 6, потім 26).

# 

# \## Залишковий ризик

# 

# Заголовки Content-Security-Policy і X-Frame-Options не додавались (їх не було в ЛР 5, на рівні «Задовільно» це не вимагається). Поведінку за зворотним проксі чи на реальному розгортанні не перевірялось.

# 

# \## Доказ

# 

# Production-like профіль, POST /api/auth/login при недосяжній базі; порівняння заголовків 500 до і після виправлення (curl із виводом заголовків); коміт 4ce3215. Значення cookie, токенів і паролів у доказі немає.
